# G2 CRM OTP provider (UnderCodeEC)

**Status:** development branch only; synthetic service-to-service QA completed, not deployed or connected to a real phone/CRM account. No new accounts or roles.

Base URL is the **UnderCodeEC Express API**, not the Next.js site or its `/api/hermes/*` proxy. The existing web client defaults to `https://api.undercodeec.com` (`NEXT_PUBLIC_API_URL` overrides it); production availability of these new routes has **not** been verified.

1. `POST {UNDERCODE_API_BASE_URL}/api/crm/auth/request-code` with `{ "email": "<authorized operator email>" }`. Same endpoint for web and mobile; generic success response to avoid email enumeration, 429 when socket-peer rate limited. Sends the existing email OTP.
2. **Mobile only:** `POST {UNDERCODE_API_BASE_URL}/api/crm/auth/mobile/verify-code` with `{ "email": "...", "code": "<8 digits>" }`. On success returns **only** `{ "success": true, "proof": "<JWT>" }`; never creates or returns an UnderCode admin session. Invalid/expired OTP returns 400; rate limit returns 429. No secret or admin token belongs in the app.
3. Existing web route `/api/crm/auth/verify-code` stays unchanged at the contract level: `{ success, proof, adminToken }`. Both verifiers consume the **same** one-use OTP, atomically. The mobile JWT keeps the existing issuer `undercodeec-admin`, operator subject, `ADMIN` role, HS256 signing secret `CRM_HERMES_PROOF_SECRET`, and 120-second lifetime, but has distinct audience **`hermes-crm-mobile`**. Web audience remains **`hermes-crm`**.

HTTP errors: invalid, expired or already consumed OTP returns 400 from either verifier; request/verify limits return 429. A mail-send failure returns 500 and revokes its reserved OTP (including across requests backed by the same MySQL store). A missing signing secret returns 500 **before** consuming an OTP. Neither error response includes a proof or admin token. A caller-supplied `X-Forwarded-For` never changes the rate-limit peer key.

Hermes must implement its **separate mobile exchange endpoint**: verify HS256 with a server-only secret, exact issuer/subject/role/audience, expiry and unique `jti`; atomically mark `jti` used in durable shared storage (not a per-process map), then issue a Hermes mobile-scoped session. Reject mobile proofs on the web exchange and web proofs on the mobile exchange. The OTP is single-use in UnderCodeEC; **JWT replay prevention belongs to Hermes**. Do not ship the proof signing secret to the app. No UnderCodeEC-side Hermes exchange is implemented here.

OTP, email cooldown, per-IP request limit, per-IP verify limit and global per-code attempts now use transactional MariaDB/MySQL tables `crm_auth_otp` and `crm_auth_limits`. Apply `backend/sql/20261117_crm_auth_otp.sql` explicitly to the **verified** database before starting the changed API; runtime only checks that the tables exist and fails closed otherwise. No DDL privilege is required for the API user. A failed DB operation fails closed; failed mail delivery revokes the reserved code. Keys use socket peer IP hashed before storage: arbitrary `X-Forwarded-For` is ignored. Behind a reverse proxy, all traffic via the same peer shares the IP limit; configure/protect upstream per-client limiting before rollout if that affects legitimate users. Existing web `adminSessions` are **still process-local**; web admin-token use must stay on a sticky/single backend or be migrated separately. Mobile does not create one, so this is not a mobile auth dependency. All environments must use the same database and OTP/proof secrets; multi-node DB isolation or signing-secret mismatch blocks interoperability.

Validation from this worktree: `npm --prefix backend run test:crm-auth` runs the HTTP contract tests (loopback Express/fetch, fake injected sender/store, no external SMTP), JWT signature/claims tests, and store tests. `npm --prefix backend test` also runs the full backend suite. Neither command needs MySQL by default: the four MySQL cases are skipped. To run **all** CRM tests against a newly created, disposable local MariaDB, use the `desktop-linux` Docker context, a unique container name, `-p 127.0.0.1::3306`, a fresh `crm_otp_test` database and a throwaway password. Wait until a TCP SQL query against **that database** succeeds (a container-local `mariadb-admin ping` can respond during initialization). Then set `CRM_OTP_TEST_DB=crm_otp_test`, `CRM_OTP_TEST_PORT=<mapped local port>` and `CRM_OTP_TEST_PASSWORD=<throwaway password>` in the test process and run `npm --prefix backend run test:crm-auth` or `npm --prefix backend test`. The opt-in cases install `backend/sql/20261117_crm_auth_otp.sql` into **that** database, use real MySQL transactions across store instances, and make real HTTP requests with a fake mail sender; they cover both replay directions, concurrent web/mobile verification and mail-send revocation. Do not point these tests at an existing or production database; remove only the test container afterwards. No identity fixture or runtime authorization override is required; production operator checks stay unchanged. No production deployments or Hermes code changes are part of G2.

The HTTP cross-service check was repeated with the formatted Hermes test and passed (one check, no real mail or Meta). Web revocation was exercised through the API, not through the browser UI.

**Subsequent schema-drift hardening:** OTP store startup checks every column it uses in `crm_auth_otp` and `crm_auth_limits` with read-only `SELECT ... LIMIT 0`. A pre-existing table missing a required column fails closed before issuing an OTP, without runtime DDL. A new test asserts this behavior; **16/16** CRM auth tests passed, including four MariaDB opt-in tests on a fresh container removed afterwards. This verifies column presence, **not** compatible types, constraints, index shape or production DML permissions; DBA migration review and isolated backup/restore remain gates.

**Rollout gate (not executed):** verify the target DB and backup; apply the SQL additively through the approved migration procedure before updating any API instance, and check the schema and required DML permissions without exposing connection strings. Use the same shared DB and signing configuration across instances. The old in-memory OTP cannot verify codes saved in the new tables, so coordinate a brief login interruption and expiry of pending OTPs during upgrade/rollback. Reverting the app should leave the additive tables untouched (never drop login records in an automatic rollback); rotate/reissue any outstanding proofs and allow their short lifetime to elapse. Confirm web and mobile routes independently in staging first.
